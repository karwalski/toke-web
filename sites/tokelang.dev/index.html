A Language Built for AI

A programming language purpose-built for LLM code generation. Fewer tokens. Faster inference. Lower cost.

Get startedWhy toke?GitHub

The Problem

Every time an AI writes code, it generates one token at a time. Each token costs compute, time, and money. Today's programming languages were designed for humans — they're full of verbose keywords, boilerplate imports, and ceremony that LLMs must produce token by token.

toke is a programming language designed from first principles to minimise the number of tokens an LLM needs to generate. The result: AI writes equivalent programs using 2–4x fewer tokens than C or Java, directly reducing inference cost and latency.

What is a token? LLMs don't read characters — they read tokens, which are chunks of text (roughly 3–4 characters each). The word return is one token. The keyword < in toke means the same thing but is also one token — saving 5 characters of output every time the AI returns a value.

With Best Practices

Real-world code isn't minimal. Teams use documentation comments, descriptive names, and type annotations. Here's the same function written to production standards — and how that affects token cost.

m=arrproduct;f=product(arr:@u64):u64{let p=mut.1;let q=arr.len;lp(let i=0;i<q;i=i+1){p=p*arr.get(i);};<p};
18 tokens — purpose-built tokenizer (Gate 1 measured)
toke has no comments and no best-practices overhead. The program is the documentation — the type signature and structure are unambiguous. The token count is identical regardless of coding style. 
def compute_array_product(
    input_array: list[int],
) -> int:
    """Compute the product of all elements in an unsigned integer array.

    Args:
        input_array: A list of non-negative integers.

    Returns:
        The product of all elements. Returns 1 for empty arrays.

    Raises:
        ValueError: If any element is negative.
    """
    accumulated_product = 1
    for current_element in input_array:
        accumulated_product *= current_element
    return accumulated_product
101 tokens — cl100k — function with docstring & descriptive names
Adding a standard docstring with Args/Returns/Raises sections and descriptive variable names like accumulated_product more than triples the token count: 30 → 101 tokens. The docstring alone costs ~45 tokens. 
#include <stdint.h>
#include <stddef.h>

/**
 * Compute the product of all elements in an unsigned integer array.
 *
 * @param input_array Pointer to the first element of the array.
 * @param array_length Number of elements in the array.
 * @return The product of all elements. Returns 1 for empty arrays.
 */
uint64_t compute_array_product(
    const uint64_t *input_array,
    size_t array_length
) {
    uint64_t accumulated_product = 1;
    for (size_t index = 0; index < array_length; index++) {
        accumulated_product *= input_array[index];
    }
    return accumulated_product;
}

Javadoc and camelCase descriptive names push Java from 43 → 91 tokens. Java's camelCase is slightly more token-efficient than Python/C underscores — computeArrayProduct is 3 tokens vs compute_array_product at 3 tokens.

Best practices multiply the gap. With documentation and descriptive names, toke's advantage is dramatic: 5.3x vs Python (18 vs 101), 7.2x vs C (18 vs 137), 4.8x vs Java (18 vs 91) — and toke's 18 tokens includes the complete program. In real codebases where every function has comments and descriptive names, the cumulative savings are substantial.

Why This Matters

3–9x Fewer Tokens

AI generates toke programs using a fraction of the tokens needed for C or Java. The purpose-built tokenizer achieves ~9x vs C, ~6x vs Java, ~3.5x vs Python for complete programs — measured across 46,730 verified programs in the training corpus.

Designed for Correctness

LL(1) grammar, 12 keywords, minimal character set (56 characters). No ambiguity, no implicit coercions, full static type checking. The compiler catches mistakes before code runs — critical when AI is writing the code.

Standard Library with C Runtime

30+ standard library modules with C runtime implementations — strings, files, JSON, HTTP server, database, crypto, encoding, encryption, JWT auth, WebSocket, SSE, routing, templates, CSV, math, LLM integration, charting, dashboards, and machine learning. Common operations become single function calls.

Open Source

MIT and Apache 2.0 licensed. Built in public. Every component — compiler, spec, corpus & tokenizer, benchmarks, docs, MCP server — is open for contribution and enterprise use.

Quick Example

m=hello;
i=io:std.io;

f=main():i64{
  io.println("Hello, world!");
  <0;
};

A complete toke program. m= declares the module. i= imports a library. f= declares a function. < returns a value. Every statement ends with ;. No boilerplate, no ceremony.

Phase 1Can AI write toke?

The first phase answers a simple question: can existing AI models write valid toke programs, and does toke actually use fewer tokens than conventional languages? Everything built here is designed to prove — or disprove — the core thesis before investing further.

Epics 1.1–1.10. Gate 1 criteria: >10% token reduction vs Python/C/Java (cl100k_base) AND Pass@1 ≥ 60% on held-out benchmark.

Defined the complete toke language — grammar, keywords, types, operators, and the character sets for both profiles.

LL(1) grammar, 12 keywords. Phase 1 (80 chars) for corpus generation. Phase 2 (56 chars) production encoding with $ type sigils and @() arrays. Formal EBNF, RFC draft, mechanical transformation rules. toke

1.2Reference CompilerComplete

Built the compiler that checks every toke program for correctness — type safety, syntax validity, and character set compliance.

Single-pass C99 compiler: lexer, LL(1) parser, name resolution, type inference, LLVM IR codegen (x86-64, ARM64). --check mode for corpus validation. Structured JSON diagnostics. 600+ conformance tests. toke

Built a library of 46,754 verified toke programs using three AI models in parallel (Haiku 4.5, GPT-4.1-mini, Grok-3-mini), each validated by the compiler and cross-checked against reference implementations in Python, C, and Java.

339 task templates, 50K generated tasks. 4 corpus stages: 26,978 single-function (Stage A), 9,776 multi-function (Stage B), 5,000 edge cases (Stage C), 5,000 application-level (Stage D). Auto-fixer rescues ~15% of programs at zero API cost. toke-model

1.6Gate 1 EvaluationComplete

Final benchmark on 1,000 held-out tasks. Gate 1: PASS (2026-04-03). Token reduction 12.5% (target >10%). Pass@1 63.7% (target ≥60%). Compilation rate 92.3%.

1,000 held-out tasks, 120 test inputs each. Token reduction: 12.5% (8K vocab) / 13.1% (32K vocab) vs cl100k_base. Pass@1: 588/923 compilable tasks (63.7%) via Qwen 2.5 Coder 7B + QLoRA adapter. toke-eval

2.1Language Extensions & Default SyntaxComplete

Adopted the 56-character encoding as the default (“toke”) and the 80-character encoding as the legacy profile (--legacy). Expanded the standard library to 30+ modules covering security, networking, data processing, visualization, and LLM integration.

Decision 2026-04-04: 56-char is default, $ type sigils, @() arrays, [] removed. 30+ stdlib modules with .tki interface contracts. toke

2.2Purpose-Built TokenizerComplete

Custom BPE tokenizer trained on toke programs. Patterns like $type, @(), m=, and f= become single tokens.

8K BPE, 15.2% token reduction vs cl100k_base, 7.5% char-to-token improvement. All 14 key default-syntax patterns tokenize as single tokens. SentencePiece on 46,730 programs, 100% round-trip fidelity. toke-model

2.3First Fine-Tuned Model (Gate 1)Complete

QLoRA fine-tune of Qwen 2.5 Coder 7B on the Phase 1 corpus. 73,000 training examples across direct generation and multi-language comparison formats. This model passed Gate 1 but was trained on the legacy 80-char syntax.

QLoRA rank 64, alpha 128, cosine schedule. ChatML instruction format. Gate 1 PASS: 63.7% Pass@1, 12.5% token reduction. toke-model

2.5Phase 2 Corpus & Gate 2On Hold

The entire Phase 1 corpus (46,754 programs) was mechanically transformed to the new default syntax and passes tkc --check at 90%. However, the model trained on this corpus struggled with default-syntax generation — programs compiled but many produced incorrect output. The root cause: stub stdlib functions (91 stubs across 19 modules) that return zero values, causing programs that compile successfully but behave incorrectly at runtime.

An LLM-driven refinement pipeline was built (Anthropic Sonnet, max 10 compile-feedback turns per program) that achieves 99% compilation and 98% output correctness at $0.03/record. Pilot runs validated the approach on 400 benchmark tasks with zero Python contamination. Full-scale regeneration of ~18K training records is pending local compute availability. toke-model
